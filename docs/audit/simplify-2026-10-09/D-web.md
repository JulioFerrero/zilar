# D-web: audit of apps/web/src (50.8k src lines, 238 files)

## 1. Summary

- **One 1,437 KB JS chunk (416 KB gzip), zero code splitting.** No `lazy()`/`import()` that works; all 22 route pages, the full markdown stack and the whole mock backend are in the entry chunk. Vite warns about it on every build. CSS is fine (57 KB, 11.5 KB gzip).
- **The mock backend ships to production: ~112 KB minified (8%).** `src/mock/*` (api.ts 4,297 lines, messages.ts 1,148, ...) plus `store/mockStore.ts` (1,294 lines) are statically imported by `lib/api.ts`, `lib/tools.ts`, `store/store.ts`, and `ChatStoreProvider`. The gate `isMockMode()` is a runtime check, so nothing is tree-shaken. Mostly test infrastructure (33 test files use `createChatStore`).
- **Biggest runtime-perf problem: `useChatStore()` subscribes a component to the WHOLE store state.** 34 call sites, including `MessageBubble` (per message) and `ChatListItem` (per chat). `MessageBubble` is not `memo`ed and only reads `mediaTrustedHosts`. Every typing event, presence change, draft token or message in ANY chat re-renders every bubble and chat row. The message list is not virtualized. `useAtomValue(atom, selector)` already exists in `@effect/atom-react`.
- **Biggest maintainability problem: 7 giant "panel" components with copy-pasted helpers.** `TopicPanel` (1,170 lines, 700-line body), `GroupPanel` (1,030), `ChannelPanel` (599), `AiPanel` (870), `Composer` (1,134 lines, ONE 1,050-line function), `MessageBubble` (838), `PackEditor` (783). GroupPanel and ChannelPanel have the same `roleLabel`, `GroupAiRow`, and failure plumbing. 35 `Data.TaggedError` classes are declared per component (`StoreFailed` x3, `KeyMissing` x2, `SaveFailed` x2).
- **UI kit is well adopted** (Dialog in 11 files, Sheet 5, StateMessage 7, Button 22+): a keep-as-is verdict for dialog and state shells. Gaps: `Card`/`SectionLabel` is used by only 4 pages while 33 places hand-roll `rounded-xl border`; the member-pick checkbox row is hand-rolled 5 times.
- **Dead code is small:** 0 unused components or routes; only 2 truly dead functions (`listTopicApprovalRules` in `lib/api.ts:728`, `currentSubscription` in `lib/push.ts`) and ~60 exports that are only `export`ed for tests. Unused/misplaced deps: `scheduler` pin duplicates a second copy in the bundle (3.4 KB), `radix-ui` umbrella package used only for `Slot` in one file.
- **Effect is tree-shaken adequately:** 169 KB of the bundle (12%), mostly runtime core + Schema + atoms + HTTP client; it is a fixed cost, not a leak.

## 3. Findings (ranked by value/effort)

### W1. Mock backend and mock store are in the production bundle (~112 KB min, ~8%)
Evidence: `lib/api.ts:4-5` imports `isMockApiEnabled` and `mockRequest` from `@/mock/*`; same in `lib/tools.ts:9-10`; `store/store.ts:39` re-exports `createChatStore` from `./mockStore`; `ChatStoreProvider.tsx:22` does `isMockMode() ? createChatStore() : createRealChatStore()`; `StickerPanel.tsx:21-22` imports `mockGifItems`; `AuthProvider.tsx:8-9` imports `currentUserId` from mock. `mock/gate.ts:34` decides at runtime (`import.meta.env.VITE_MOCK` / `DEV`). The bundle contains the fixture strings ("Acme Announcements" present).
Root cause: the mock path is a runtime `if`, so bundlers cannot drop it. Its real consumers are tests (33 test files use `createChatStore`; 15 use `setMockDelay`) plus dev `?mock=1`.
Impact: -112 KB min (~-30 KB gzip) from the entry chunk; also clarifies that 7.3k lines (mock/api.ts + messages + mockStore + others) are test/dev tooling.
Risk: low-medium. Tests rely on `MODE === 'test'` mock mode (`gate.ts:15`). Detect with the existing 1,000+ web tests.
Effort: S-M. Recommendation: (1) make the gate a build-time constant (`import.meta.env.VITE_MOCK === '1' || import.meta.env.DEV` / `MODE==='test'` are statically replaced by Vite, so `if (isMockMode())` branches fold if written inline as `import.meta.env.…`), and (2) load `@/mock/api` and `mockStore` only through `await import()` inside those branches. Verify by grepping the new build for "Acme Announcements" (must be 0) and `dist` size. Later (L): move `src/mock` + `mockStore` to a `test-support` dir to make intent explicit. Also fix the ineffective-dynamic-import warning in `mockStore.ts:844/859/898` (just import statically from there once the whole file is lazy).

### W2. `useChatStore()` = whole-state subscription; bubbles and rows not memoized; list not virtualized
Evidence: `ChatStoreProvider.tsx:49-51`: `useAtomValue(useChatStoreApi().atom)` where the atom holds the entire `ChatStoreState` (`store/atomStore.ts:36-42`, replaced wholesale on every `setState`, `atomStore.ts:55-57`). 34 call sites of `useChatStore()`; the hot ones:
- `MessageBubble.tsx:238-239` (`const store = useChatStore()`), the only use is `store.mediaTrustedHosts` at line ~270. No `memo` (components grep: only MarkdownText has `memo`).
- `ChatListItem.tsx:33,36-45`: reads `store.messages(chat.id)`, `store.currentUserId`, `store.typing[...]`, `store.drafts[...]`.
- `MessageList.tsx:41,249`: `items.map(...)` renders every loaded message; no windowing (grep for virtual/content-visibility: nothing). Also `groupMessages(...)` and a new `draftMessage` with `new Date()` are rebuilt on each render (`MessageList.tsx:~83-90`).
- `ChatList.tsx:61-63`: `visibleChats(store)`, `groupChats(store)`, `archivedChats()` recomputed on every store change; `ChatList` re-renders on every typing tick anywhere.
Mitigating fact: `messages(chatId)` returns the same array reference per chat (`realStore.ts:1479`: `get().messagesByChat[chatId] ?? []`), so `memo` would be effective on message objects if callbacks are stable.
Impact: streaming AI drafts (`store.drafts`), typing events and presence cause a full re-render of the entire message list and chat list; cost grows with messages loaded (no cap/virtualization). Estimated reduction of render work from O(all bubbles) to O(changed bubble) per event. UNVERIFIED in a profiler (I did not run the app).
Risk: medium; selector equality must be right (arrays/objects built in selectors re-render each time).
Effort: M. Recommendation, in order: (a) add `useChatSelector(sel)` = `useAtomValue(atom, sel)` (signature exists in `@effect/atom-react` Hooks.d.ts:52+) in `ChatStoreProvider.tsx` and convert `MessageBubble` (select `mediaTrustedHosts` only) and `ChatListItem` first; (b) `memo(MessageBubble)` and stabilise `onReply/onForward/selection` props in `MessageList`; (c) for `MessageList` select just `messagesByChat[chat.id]`, `drafts[chat.id]`, `chatPrefs`; (d) later consider `content-visibility: auto` on bubbles or windowing if chats of thousands of messages are real. Keep `useChatStoreApi().getState()` for actions (already the pattern).

### W3. No code splitting: lazy-load settings routes, markdown, and auth
Evidence: `routes/AppRoutes.tsx:1-31` imports all 22 pages statically; `main.tsx` imports one `App`; Vite reports one chunk. Settings-only code: `PackEditor` 10.5 KB, `AiPanel` 12.2, `StickersPage` 12.0, `IntegrationsPage` 10.0, `ToolDetailPanel` 8.4, `NotificationsPage` 8.4, plus `MachinesPage`, `ConnectionsPage`, `ApprovalsPage`, `FoldersPage`, `SetupPage`, `LoginPage` (+ better-auth ~25 KB), all about 180-220 KB min together (estimate from the per-file numbers). Markdown (~120 KB min) is used only by `MessageBubble.tsx:26,691` for AI replies and `markdownToPlain`.
Impact: first load could drop from 416 KB gz to roughly 250-280 KB gz (estimate: settings routes ~50 KB gz, markdown ~40 KB gz, mock ~30 KB gz, login/auth ~10 KB gz). Chat-first PWA, repeat visits are cached by the service worker anyway, so the main win is first load/cold start on mobile networks.
Risk: low (React.lazy + Suspense with the existing `StateMessage`/`Skeleton` fallback); the `SKELETON_DELAY_MS` pattern already exists. Test files render routes via `renderApp`; lazy components need `await findBy*` (some tests may need `waitFor`).
Effort: S for routes (convert `/settings/*` + `/login` + `/setup` + `/welcome/*`), M for markdown (`React.lazy(MarkdownText)` with plain-text fallback, since tests render synchronously).
Recommendation: do W1 first (free), then lazy routes, then markdown. Add `build.rolldownOptions.output.codeSplitting` only if needed; plain dynamic imports are enough.

### W4. Panel components: duplicated helpers and god functions
Evidence (duplication):
- `roleLabel` identical: `GroupPanel.tsx:55-57`, `ChannelPanel.tsx:39-41`.
- `GroupAiRow` implemented twice: `ChannelPanel.tsx:517`, `GroupPanel.tsx:598` (same remove-AI + confirm + error flow; different failure types).
- Failure plumbing triplicated: `GroupPanel.tsx:60-107` (`PanelFailure`, `apiStep`, `storeStep`, `apiFailureText`), `ChannelPanel.tsx:45-82` (`StoreFailed`, `storeCall`, `failureText`, `describeFailure`), `ExplorePage.tsx:33` and `VisibilitySection.tsx:17` (`StoreFailed` again).
- 35 local `Data.TaggedError` classes (grep), including duplicates of the same name: `StoreFailed` x3 (ExplorePage:33, ChannelPanel:45, VisibilitySection:17), `KeyMissing` x2 (ConnectionsPage:38, SetupPage:20), `SaveFailed` x2 (ChatBackgroundDialog:35, HandlePage:43). Many are payload-less "this call failed, show text X" markers that exist only to feed `useAction<_, _, E>`.
- Member/AI/role pick rows `flex cursor-pointer items-center gap-3 rounded-lg px-2 py-2 hover:bg-list-hover`: `ForwardPicker.tsx:111`, `NewGroupDialog.tsx:189`, `NewTopicDialog.tsx:260,294,320`. The role chip `font-mono rounded-[5px] border border-badge-muted ...` appears 6x (AiBadge, ChatListItem x2, GroupPanel x2, ChatHeader, TopicPanel, TaskStrip, ChannelPanel, NewTopicDialog), while `well`/`chip` kit pieces exist.
- NewGroupDialog vs NewTopicDialog (364 lines each): differ in 604 diff lines, i.e. similar shape (name field, member checkboxes, create failure), different content; a shared `PickList` row component is the realistic extraction, not a merged dialog.
- `TopicPanel`: `TopicPanelBody` lines 90-795 is one 700-line function with 15 `useState`; add/remove member/AI buttons (`:796-930`) are four near-identical small components. `Composer` is one function lines 87-1134 with 24 `useState/useRef`, 12 `useEffect` (voice recording, mentions, stickers, attachments, typing in one place). `MessageBubble` function 219-838 (620 lines).
Impact: roughly 300-500 lines removable from GroupPanel/ChannelPanel/TopicPanel/dialogs by extracting `components/panel/` shared pieces (`MemberRow`, `GroupAiRow`, `roleLabel`, a `useStoreAction(call, fallback)` helper in `lib/effect/`) and a single `StoreFailed` in `lib/effect/errors.ts`. Estimate method: the duplicated blocks above are ~25+60+40+40 lines each x2-3 copies. Larger win is clarity/test speed (splitting Composer into `useVoiceRecorder`, `useMentionPicker`, `useAttachmentDraft` hooks, each testable without rendering the full composer; current Composer tests: Composer.test + Composer.voice.test).
Risk: medium for Composer (touch handling, recorder lifecycle), low for the panel helpers.
Effort: M for the shared helpers; L for Composer/TopicPanel/MessageBubble splits. Do one panel per task, with existing tests as the net.
Why it exists: each task was specced as a self-contained "convert this component to Effect" pair (see memory: Effect pairs plan), so every component got its own tagged errors and helpers. Fix at the structure level: one `useStoreAction`/`useApiAction` in `lib/effect/use-action.ts` that maps ApiError/Error/unknown to a message string would make most local error classes unnecessary.

### W5. Dead and over-exported code (small)
Evidence: script over 936 exports (scratchpad/audit/unused.txt): 227 are never referenced from non-test code. Almost all are `export` kept for tests or type-only (`*Props`, Zod-era `*Schema` exports in `lib/api.ts` such as `topicKindSchema`, `pinSchema`, `machineSchema`; `lib/voice.ts` `*Effect` variants and constants; `lib/push.ts` helper types). Truly dead (1 occurrence = definition only):
- `lib/api.ts:728 listTopicApprovalRules` (no caller in web, mock or mobile).
- `lib/push.ts currentSubscription`.
Unused-in-prod but used by tests only (decide per case): `lib/format.ts formatLastSeen` (used internally), `store/effects/ports.ts testPorts`/`PortsTest`, `lib/handles.ts normalizeHandle/isReservedHandle`, `store/effects/prefs.ts applyPrefs`.
Dead components/routes: none. Every file in `components/` and `routes/` is imported somewhere in prod code, and all 22 route elements are mounted in `AppRoutes.tsx`. 17 `*.fixture.tsx` files are for React Cosmos (dev only; not in the bundle).
Impact: <100 lines; value is lower API surface. Effort: S. Recommendation: delete the 2 dead functions; add `knip` (or oxlint `no-unused-exports` equivalent) to CI to stop growth; do not mass-un-export schemas (the other auditor owns `lib/api.ts`).

### W6. Dependencies
- `scheduler` is a direct dependency of web (`package.json`, pinned `^0.27.0`) with zero imports in `src`. It exists as a peer of `@effect/atom-react` (range `>=0.25.0 <0.28.0`), while react-dom 19.3 brings `scheduler@0.28.0`. The bundle therefore carries both (3.4 KB each). Saving 3.4 KB min. Check whether atom-react can use 0.28 (peer range stops at <0.28; watch for an update) before removing; UNVERIFIED that atom-react uses it at runtime in browser.
- `radix-ui` (umbrella) is used only for `Slot` in `components/ui/button.tsx:2`. Tree-shaking works (2.3 KB in bundle), but the install pulls ~50 radix packages. Replace with `@radix-ui/react-slot` or a 10-line `asChild`. Install-time only.
- `class-variance-authority`, `clsx`, `tailwind-merge`: 27 KB for tailwind-merge. Kept: used in `cn()` everywhere; the cost is acceptable. A cheaper variant is a `cn` without twMerge if conflicts are rare. Not recommended.
- Duplicate libs in the bundle: none besides scheduler (react 19.3.0 only; 19.2.3 is mobile's, not bundled). `effect@4.0.0` is only used by runner/devtools.
- `better-auth` 25 KB: only needed on `/login` (see W3).
- Markdown stack ~120 KB min for rendering AI replies: heavy for the use (`MarkdownText.tsx` only enables GFM + safe links). `micromark` family cannot be shrunk by config. Alternatives: lazy-load (W3) or a small custom renderer; do not replace.

### W7. Kit adoption gaps (settings/cards)
Evidence: `ui/card` (`Card`, `SectionLabel`) imported by 4 route files (Requests, Notifications, Folders, Blocked) while the same surface is hand-rolled at `machines/ApprovedMachineCard.tsx:89`, `PendingMachineCard`, `RevokedMachineCard`, `FolderEditorDialog` (5x), `StickersPage` (3x), `IntegrationsPage` (3x), `ConnectionsPage` (2x), `ProfileSettingsSection` (2x), `PackEditor` (2x), `TaskStrip`, `AisPage`, `NotificationsPage`: 33 `rounded-xl|2xl border` occurrences. Four `<select>` elements repeat the same `well-surface rounded-[10px] px-3 py-2 ...` class string (AiPanel:625, TopicPanel:1143, NewTopicDialog:334, ConnectionsPage:323); kit has `text-input`, `segmented-control` but no `Select`. Error text: 52 `role="alert" ... text-danger` paragraphs; `StateMessage kind="error"` handles block/inline states but not field-level errors; a `FieldError` kit piece would cover them.
Settings pages: 11 routes all wrap in `SettingsShell` (good, `components/SettingsShell.tsx`). Loading/empty/error states: consistent via `StateMessage` (21 uses).
Impact: ~150-250 lines and visual consistency; no perf effect. Effort: S-M, mechanical. Recommendation: add `ui/select.tsx` and `ui/field-error.tsx`, then migrate with one task per directory. Low priority.

### W8. Store layering (web-only view)
`store/mockStore.ts` (1,294 lines) and `store/realStore.ts` (1,680) both implement the same `ChatStoreState` (80 and 86 action names, 80 identical). `store/store.ts` (585 lines) is the interface plus re-exports. Since the mock is now only test/dev (W1), the parallel implementation is a maintenance tax: every new action needs a mock twin. Option: tests build `createRealChatStore` with fake ports (`store/effects/ports.ts` already has `PortsTest`/`testPorts`), and drop `mockStore` entirely. That would remove ~1,300 lines and rework 33 test files. Effort L; do it after W1 and only if mock-twin edits keep recurring (check `git log --stat -- apps/web/src/store/mockStore.ts` frequency, UNVERIFIED).

## 4. Things that look bad but should stay

- **Single `Dialog`/`Sheet`/`useModal` shells** (`components/ui/dialog.tsx` 83 lines, `sheet.tsx` 56, `use-modal.ts` 95): well used (11 and 5 importers), no hand-rolled modals (`fixed inset-0`: 0 hits outside kit). Keep.
- **Two React contexts only, no prop-drilling problem:** `AuthContext` and `ChatStoreContext` (value is the stable store object). The Provider values are not recreated per render. The drilling is shallow (panel -> row). Keep.
- **Effect in the browser (169 KB):** core `internal/effect`, Schema and atoms are needed by store and API client; tree-shaking worked (only `effect`, `effect/reactivity`, `effect/http` entry points imported). Replacing would be a rewrite for ~100 KB. Keep.
- **Fonts:** 11 Geist subset woff2 files look heavy but are `unicode-range` split; latin only costs ~52 KB. Keep.
- **lucide-react:** per-icon imports, 24 KB total. Keep.
- **`useAction`/`useQuery` wrappers in `lib/effect/` (341 lines total):** small, shared by 40+ call sites; the right place to fix W4.
- **Per-feature polling hooks** (`usePendingApprovalCount` 46, `useContactRequestCount` 53, `useApprovalPolling` 233): similar shape but different semantics (on-open fetch vs 60 s loop vs visibility-aware polling). Merging gives little.
- **Eager `AppRoutes`** is a reasonable choice for a chat-first PWA with a service worker; only the lazy candidates in W3 are worth splitting.
